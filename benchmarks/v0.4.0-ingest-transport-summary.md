# v0.4.0 Ingest Transport Summary

Reference run date: **April 6, 2026**

Reference machine:

- `uname -a`: `Darwin macbook 25.4.0 ... arm64`
- CPU: `Apple M4 Pro`
- Toolchain: `nix develop -c zig version` -> `0.15.1`

These numbers are a checked-in preview-readiness baseline, not a performance promise. The main goal is to keep the local-ingest story honest relative to the real live HTTP path and to make transport-bound vs storage-bound regressions obvious.

## Commands

```sh
nix develop -c zig build bench-ingest-transport -- --scenario one_hot_one_writer
nix develop -c zig build bench-ingest-transport -- --scenario fanout_four_writers
nix develop -c zig build bench-ingest-transport -- --scenario warm_declared_10k
nix develop -c zig build bench-ingest-transport -- --scenario cold_declare_10k
nix develop -c zig build bench-ingest-transport -- --scenario steady_state_100k
```

Benchmark notes:

- The HTTP lane now uses the real `sydradb serve` process and `POST /api/v1/ingest`.
- The live HTTP server now handles `Expect: 100-continue` correctly; the benchmark client still sends `Expect:` empty for multi-writer POST stability and single-response parsing.
- Benchmark lines now split `active_ms` from `barrier_ms` and include writer-loop phase totals (`wal_s`, `memtable_s`, `flush_s`) plus tag-index persistence counters.
- The direct-engine cold scenario now includes declaration work inside the timed window.

## Gate Readout

Promotion gates are now split by workload class.

Transport-bound scenarios:

- warm UDS must stay within 25% of direct-engine throughput
- warm UDS must beat live HTTP by at least `1.5x`

Observed:

- `one_hot_one_writer`: pass on both gates
  - UDS is about `77%` of direct engine
  - UDS is about `32.65x` faster than live HTTP
- `fanout_four_writers`: pass on both gates
  - UDS is slightly faster than direct in this sample
  - UDS is about `10.72x` faster than live HTTP
- `steady_state_100k`: pass on both gates
  - UDS is about `93%` of direct engine
  - UDS is about `61.85x` faster than live HTTP

Storage-bound scenarios:

- warm/cold UDS must stay within 10% of direct-engine throughput
- live HTTP stays a reference number and is not a promotion blocker

Observed:

- `warm_declared_10k`: pass
  - UDS is effectively at direct-engine parity
  - the output now makes the bottleneck obvious: almost all time is barrier/flush, not transport
- `cold_declare_10k`: fail
  - UDS is about `69%` of direct engine
  - the remaining gap is dominated by cold declaration cost (`local_declare_s=0.505645`)

## Conclusion

The local socket path is now clearly the right same-host exact-series transport in transport-bound workloads, and the benchmark output itself shows why: warm UDS stays close to direct-engine throughput while live HTTP remains far slower.

The remaining promotion blocker is no longer `warm_declared_10k`. That case now behaves like a true storage-bound workload and UDS is already at direct-engine parity there.

The remaining blocker is `cold_declare_10k`: declaration-heavy cold starts still cost substantially more over the socket path than the direct-engine baseline. That means the next exact-series performance work should stay focused on declaration-path cost and storage-side batching rather than adding broader socket scope.
