# v0.4.0 Ingest Transport Summary

Reference run date: **April 6, 2026**

Reference machine:

- `uname -a`: `Darwin macbook 25.4.0 ... arm64`
- CPU: `Apple M4 Pro`
- Toolchain: `nix develop -c zig version` -> `0.15.1`

These numbers are a checked-in preview-readiness baseline, not a performance promise. The main goal is to keep the local-ingest story honest relative to the real live HTTP path and to make transport-bound vs storage-bound regressions obvious.

## Commands

```sh
nix develop -c zig build bench-ingest-transport -- --scenario one_hot_one_writer
nix develop -c zig build bench-ingest-transport -- --scenario fanout_four_writers
nix develop -c zig build bench-ingest-transport -- --scenario warm_declared_10k
nix develop -c zig build bench-ingest-transport -- --scenario cold_declare_10k
nix develop -c zig build bench-ingest-transport -- --scenario steady_state_100k
```

Benchmark notes:

- The HTTP lane now uses the real `sydradb serve` process and `POST /api/v1/ingest`.
- The live HTTP benchmark client now sends and handles `Expect: 100-continue` correctly instead of suppressing it.
- Benchmark lines now split `active_ms` from `barrier_ms` and include declaration-phase totals (`exact_decl_metric_s`, `exact_decl_series_s`, `exact_decl_wal_s`, `exact_decl_tag_s`) plus declaration outcome counters.
- The direct-engine cold scenario now includes declaration work inside the timed window.

## Gate Readout

Promotion gates are now split by workload class.

Transport-bound scenarios:

- warm UDS must stay within 25% of direct-engine throughput
- warm UDS must beat live HTTP by at least `1.5x`

Observed:

- `one_hot_one_writer`: pass on both gates
  - UDS is about `0.946x` direct engine
  - UDS is about `45.34x` faster than live HTTP
- `fanout_four_writers`: pass on both gates
  - UDS is about `0.921x` direct engine
  - UDS is about `11.83x` faster than live HTTP
- `steady_state_100k`: pass on both gates
  - UDS is about `1.003x` direct engine
  - UDS is about `49.22x` faster than live HTTP

Storage-bound scenarios:

- warm/cold UDS must stay within 10% of direct-engine throughput
- live HTTP stays a reference number and is not a promotion blocker

Observed:

- `warm_declared_10k`: pass
  - UDS is about `0.965x` direct engine
  - the new attribution fields show the workload is still dominated by `flush_drain_wait_s` and `flush_segment_s`, not by append transport
- `cold_declare_10k`: fail
  - UDS is about `0.790x` direct engine
  - the new attribution fields show the remaining miss is split between local declaration (`local_declare_s=0.171687`) and storage-bound barrier work (`flush_drain_wait_s=0.776241`, `flush_segment_s=0.708119`)

## Conclusion

The local socket path is still clearly the right same-host exact-series transport in transport-bound workloads, and the benchmark output now makes that easier to see: warm UDS stays near direct-engine throughput while live HTTP remains far slower.

The remaining promotion blocker is still not `warm_declared_10k`. That case now passes the storage-bound gate, and the new attribution fields make it obvious that the dominant cost is the shared flush/barrier path rather than transport overhead.

The remaining blocker is `cold_declare_10k`: declaration-heavy cold starts now have much better attribution, but the preview gate still fails because the same workload remains slower end-to-end over the socket path than the direct-engine baseline. The next exact-series performance work should stay focused on cold declaration preparation, selector-key/tag-pair work, and storage-bound barrier cost rather than broadening socket scope.
